# Правила проекта

## Назначение документа

Документ задаёт единый источник истины по продуктовым решениям и границам текущей версии платформы. Все последующие этапы разработки должны соответствовать этим правилам; выход за рамки допустим только через явно утверждённые новые этапы.

---

## Продуктовые правила

### 1. Сейчас реализуется только продажа недвижимости

В объёме текущего MVP платформа поддерживает исключительно **продажу** объектов недвижимости. Функциональность, связанная с арендой (поиск аренды, типы сделок «аренда», листинги аренды и т.п.), в текущей версии не входит.

### 2. Аренда на текущем этапе не входит в MVP

Аренда явно исключена из текущего объёма работ. Не следует добавлять модели, поля, фильтры или интерфейсы для аренды до тех пор, пока это не будет включено в отдельный этап.

### 3. Публичная регистрация пользователей не реализуется

Самостоятельная регистрация посетителей сайта (форма «Зарегистрироваться», подтверждение email, самосервисное создание аккаунта) не входит в текущий MVP. Не нужно проектировать или реализовывать публичные эндпоинты и страницы регистрации.

### 4. Создание пользователей выполняет только администратор

Учётные записи пользователей (сотрудников, менеджеров и т.д.) создаются только через администрирование — внутренними средствами CRM/админки уполномоченным лицом (администратором). Публичного потока создания пользователей нет.

### 5. Встроенный чат на текущем этапе не реализуется

Функциональность чата между пользователями, клиентами и сотрудниками (в том числе виджеты чата, уведомления в реальном времени, история переписки в рамках платформы) не входит в текущий MVP. Не добавлять чат без утверждённого отдельного этапа.

### 6. Импорт объектов: только минимальный CRM-фундамент (этап 14.6)

Полноценный импорт из внешних систем (API маркетплейсов, расписания, автоматические удалённые фиды) не входит в текущий объём. Реализован **минимальный** фундамент: загрузка файла CSV или XML в CRM, ручное сопоставление полей, создание объектов **только как черновики**, учёт строк и логирование; подробности — в подэтапе 14.6. Объекты по-прежнему можно добавлять вручную через CRM; публикация импортом не выполняется.

### 7. Лишние блоки и перегруженные элементы не добавляются

Проект не должен копировать перегруженный функционал крупных маркетплейсов недвижимости (например, CIAN, Avito). Такие площадки допустимы только как **UX-референсы** (подход к фильтрам, карточкам, навигации). Запрещается добавлять блоки, виджеты и тяжёлые сценарии, не утверждённые в текущем объёме MVP (сравнение объектов, избранное в виде отдельной подсистемы, сложные рекомендации, лишние шаги в воронке и т.п.), если они не были явно включены в описание этапа.

### 8. География проекта ограничена Краснодарским краем

Платформа **не охватывает всю Россию**. География текущего MVP ограничена **Краснодарским краем**. В первой версии поддерживаются только два города: **Краснодар** и **Геленджик**. Для Краснодара платформа должна поддерживать утверждённую структуру районов / микрорайонов / населённых пунктов / сёл / деревень / хуторов / местностей. Для Геленджика — аналогично утверждённую структуру районов / микрорайонов / населённых пунктов / сёл / деревень / хуторов / местностей. Другие города, регионы и общефедеральное покрытие в текущий MVP **не входят**. Масштабирование на всю Россию не добавляется в текущей версии.

### 9. Фильтры по локации соответствуют утверждённой географии

Фильтры по местоположению должны отражать утверждённую структуру районов / микрорайонов / населённых пунктов для Краснодара и Геленджика. Универсальная общефедеральная логика выбора региона (общероссийский селектор регионов и городов) **не допускается**. Логика выбора района / населённого пункта в фильтрах должна следовать ранее утверждённой визуальной и UX-логике, зафиксированной в референсных скриншотах проекта; заменять её упрощённым универсальным селектором региона запрещено.

### Адаптивность интерфейса

Интерфейс публичного сайта и CRM должен быть адаптивным и корректно работать на мобильных устройствах, планшетах и десктопах.

Разработка интерфейса следует принципу **mobile-first**.

Для реализации интерфейса используется TailwindCSS.

Использование Bootstrap и других универсальных CSS-фреймворков не допускается.

## Что входит в текущую реализацию

- Публичный сайт недвижимости (каталог, карточки, поиск, фильтры, карта, статьи).
- Личный кабинет сотрудника: вход по email/паролю (JWT), выход, защита `/account` и каркас зоны (основной вход с сайта); прежние страницы `/crm/*` в коде сохранены.
- Внутренняя CRM для сотрудников.
- Ручное управление объектами недвижимости (только продажа).
- Заявки/лиды (формы обратной связи, запросы с сайта).
- Роли и права для персонала.
- Учётные записи пользователей создаются администратором.
- Минимальный фундамент импорта объектов в CRM (CSV/XML, черновики) — подэтап 14.6.

## Прогресс реализации (этапы)

### Архитектура: этап 1 — зона `/account` (личный кабинет) (выполнено)

- Маршруты: `/account/login` (вход сотрудника), `/account` (каркас кабинета).
- Для неаутентифицированного пользователя доступ к `/account` закрыт: `middleware` проверяет cookie-зеркало access-токена (`centreal_access`); без токена — редирект на `/account/login`; на клиенте `RequireEmployeeAuth` проверяет `localStorage` и валидность сессии через `GET /api/auth/me/`.
- Канонический вход с публичного сайта: кнопка в шапке «Вход в личный кабинет» → `/account/login`.
- Код и маршруты `/crm/*` не удалялись; корень `/crm` перенаправляет на `/account`; ссылки «войти» в CRM-компонентах ведут на `/account/login`; после успешного входа редирект на `/account`.
- В `robots.txt` для индексации закрыты и `/crm`, и `/account`.

### Архитектура: этап 2 — авторизация сотрудника (личный кабинет) (выполнено)

- Вход по **email и паролю** через существующий backend: `POST /api/auth/login/` (JWT pair), проксируется Next rewrite на Django (`users.LoginView`, `EmailTokenObtainPairSerializer`). Публичной регистрации нет.
- Учётные записи создаются только администратором; в системе нет эндпоинтов саморегистрации — войти может только пользователь, заведённый в БД.
- После успешного входа пара `access`/`refresh` сохраняется в `localStorage` (`crmAuth`), access дублируется в cookie для `middleware`; редирект на `/account`.
- Выход из кабинета: кнопка «Выйти» на `/account`, очистка `localStorage` и cookie (`clearCrmTokens`), редирект на `/account/login`.
- `/account/login` остаётся публичным; остальные `/account/*` недоступны без аутентификации (cookie + проверка токена через `/api/auth/me/`).

### Архитектура: этап 3 — роли и базовый доступ (выполнено)

- Роли сотрудника в модели `users.User`: поле `role` (`TextChoices`); минимальный продуктовый набор — **администратор** (`admin`) и **риэлтор** (`realtor`); значение **`superadmin`** сохранено и даёт тот же полный доступ к CRM API, что и `admin`.
- **Администратор** (`admin`) и **суперадминистратор** (`superadmin`): полный доступ к защищённым CRM API (включая выборки без ограничения по владельцу).
- **Риэлтор** (`realtor`): ограниченный доступ — те же эндпоинты CRM, но выборки и проверки объектов ограничивают видимость и изменение (объекты, лиды, импорт и вложенные ресурсы по правилам в `users.permissions`).
- Проверки на backend: классы разрешений DRF (`IsCrmUser`, объектные `IsCrmPropertyStaffOrOwner`, `IsCrmLeadStaffOrOwner`, `IsCrmImportJobOwnerOrStaff`) и фильтрация queryset; `GET /api/auth/me/` требует активного пользователя с одной из ролей CRM.

### Архитектура: этап 4 — базовый UI личного кабинета (выполнено)

- Маршруты кабинета под префиксом `/account` (группа `(cabinet)`): **Панель** (`/account`), **Объекты** (`/account/properties`), **Клиенты** (`/account/clients`), **Профиль** (`/account/profile`); для администраторов в боковой панели дополнительно **Сотрудники** (`/account/staff`).
- Каркас кабинета: боковая панель + основная область контента; навигация и кнопка «Выйти» в сайдбаре; страницы-заглушки без бизнес-логики.
- Разделение навигации по роли на основе ответа `GET /api/auth/me/` (`role`): роли **`superadmin`** и **`admin`** видят пункт «Сотрудники»; **`realtor`** — только Панель, Объекты, Клиенты, Профиль. Права доступа по-прежнему определяются backend.
- Вход (`/account/login`), middleware и проверка сессии (`RequireEmployeeAuth` + `/api/auth/me/`) без изменения назначения.

### Архитектура: этап 5 — риэлторы (управление администратором) (выполнено)

- Модель `users.User`: поле **телефона** уже было (`phone`); добавлены **аватар** (`avatar`, `ImageField`, `users/avatars/`) и **`crm_id`** (уникальный текстовый идентификатор сотрудника).
- **CRM ID** генерируется автоматически при первом сохранении новой записи, формат **`RID` + 6 цифр** (`RID000001`, `RID000002`, …), не меняется при обычных обновлениях; для уже существующих пользователей значения проставлены миграцией `users.0004_user_avatar_crm_id` (по возрастанию `pk`); при коллизии уникальности при создании — повторная попытка с новым номером.
- **Только роли `superadmin` и `admin`** управляют риэлторами через CRM API: `GET/POST /api/crm/realtors/`, `GET/PUT/PATCH/DELETE /api/crm/realtors/<id>/` (права `IsCrmStaffManager`); **риэлтор** к этим операциям не допускается. Создание через API всегда с ролью `realtor`.
- **Отключение** учётной записи: `PATCH` с `is_active=false` (флаг «Активен» в модели пользователя). **Удаление**: `DELETE` по тому же ресурсу (жёсткое удаление записи пользователя).
- **Кабинет `/account/staff`**: список риэлторов с колонками CRM ID, имя, email, телефон, роль, активность, последний вход (`last_login` при наличии), аватар; действия на русском — добавить, изменить, отключить, удалить (минимальный UI на `AccountStaffRealtorsPanel`).
- Ответ `GET /api/auth/me/` дополнен полями `phone`, `crm_id`, `avatar` (абсолютный URL медиа при запросе).

### Архитектура: этап 6 — дополнительные права риэлтора в CRM (FINALIZED)

- На модели `users.User` хранятся шесть булевых флагов (по умолчанию `false`): `perm_create_property`, `perm_edit_property`, `perm_delete_property`, `perm_view_clients`, `perm_delete_clients`, `perm_change_status` — смысловые коды: **create_property**, **edit_property**, **delete_property**, **view_clients**, **delete_clients**, **change_status**.
- Роли **superadmin** и **admin** по-прежнему имеют полный доступ к CRM без проверки этих флагов; для **realtor** те же эндпоинты дополнительно проверяют нужный флаг (второй слой поверх роли и выборок/владения).
- Назначение флагов: только **администратор** через существующий CRM API риэлторов `PATCH/PUT /api/crm/realtors/<id>/` (и при создании `POST` — опционально в теле) и блок «Права в CRM» в модалке на `/account/staff`; **риэлтор** не может менять эти поля ни у себя, ни у других (доступ к `/api/crm/realtors/` по-прежнему только у staff).
- Ответ `GET /api/auth/me/` дополнен объектом `crm_capabilities`: эффективные значения шести прав (у staff всегда истина для удобства UI).
- Учёт в Django Admin: те же поля в карточке пользователя (блок «CRM: доп. права»).
- Миграция `users.0005_user_crm_permission_flags`.
- На backend флаги проверяются через `require_crm_capability` на соответствующих CRM-операциях (объекты: создание, проверка дублей, правка, публикация/черновик, архивация, фото/видео, создание задачи импорта; лиды: список/деталь и комментарии, смена статуса, **удаление лида**).
- **Удаление лида:** `DELETE /api/crm/leads/<id>/`, ответ **204 No Content**; перед удалением вызывается `require_crm_capability(..., "delete_clients")` (при отказе — **403**, текст на русском из `users.permissions`). Доступ к записи для **realtor** по-прежнему ограничен `crm_lead_queryset_for_user` / `IsCrmLeadStaffOrOwner` (чужой лид — **403**; у модели `Lead` отдельного soft-delete нет — обычное удаление из БД с каскадом связанных комментариев и истории статусов).

### Архитектура: этап 7 — профиль риэлтора (личный кабинет и публичный сайт) (выполнено)

- **Источник данных:** имя, фамилия, телефон и фото хранятся на модели `users.User` (`first_name`, `last_name`, `phone`, `avatar`); отдельный параллельный профиль для кабинета не вводился.
- **Страница `/account/profile`:** отображение и правка на русском; поля — имя, фамилия, телефон, фотография; загрузка фото — минимальная (multipart), без редактора и обработки.
- **API:** `GET` и `PATCH /api/auth/me/` под JWT и `IsCrmUser`; править можно только свою запись (объект всегда `request.user`); ответ после `PATCH` — в том же формате, что и `GET` (включая `avatar` как абсолютный URL медиа).
- **Публичная карточка объекта:** вложенный `assigned_realtor` в публичном детальном сериализаторе дополнен полем `avatar` (тот же `User.avatar`, что и в кабинете); имя по-прежнему из `first_name` / `last_name`. Раскрытие телефона (`POST .../reveal_phone/`): если задан контакт объекта с включённым показом и непустым номером — используется он; иначе при непустом `phone` у ответственного риэлтора (`assigned_realtor`) возвращается этот номер (лог `PhoneRevealLog` через `RealtorProfile`, при отсутствии профиля — автоматическое `get_or_create` по пользователю).

### Этап 8 — CRM

**Подэтап 8.1 — Каркас CRM** (выполнено).

- Разделы CRM определены.
- `/crm/login` — исправлено.
- `/crm/dashboard` — исправлено.
- `/crm/properties` — исправлено.
- `/crm/leads` — исправлено.
- `/crm/articles` — исправлено.
- `/crm/users` — исправлено.

Реализовано: канонический перечень разделов CRM (единый источник истины); минимальный layout CRM; минимальные скелет-страницы для каждого маршрута CRM.

**Подэтап 8.2 — Backend CRUD объектов в CRM** (выполнено).

- Эндпоинты CRM для объектов: список, создание, получение по id, обновление (PUT/PATCH), архивация (POST `.../archive/`).
- Отдельные CRM-сериализаторы (список, деталь, запись); публичные маршруты `api/properties/` без изменений.
- Архив: `status=archived`, снятие с публикации, `archived_at`, очистка `published_at`; отдельного soft delete нет (не используется в базовых моделях проекта).

**Подэтап 8.3 — Backend: фото объектов в CRM** (выполнено).

- CRM-эндпоинты под `/api/crm/properties/<property_pk>/photos/`: список и загрузка (POST multipart в `original_file`), деталь и удаление (`GET`/`DELETE` по id фото).
- POST `.../photos/reorder/` — тело `{"items": [{"id", "sort_order"}, ...]}`; обновление `sort_order` только для фото данного объекта.
- POST `.../photos/set_main/` — тело `{"id": <id фото>}`; один главный кадр на объект (`is_main`), остальные сбрасываются.
- Сериализаторы CRM для чтения и загрузки; производные `image_*` не генерируются на этом шаге; права `IsCrmUser`.

**Подэтап 8.4 — Backend: видео-ссылки объектов в CRM** (выполнено).

- CRM-эндпоинты под `/api/crm/properties/<property_pk>/videos/`: список (`GET`), добавление ссылки (`POST`, поля `platform`, `video_url`, `embed_url`).
- Деталь, правка (`PUT`/`PATCH`) и удаление (`DELETE`) по `/api/crm/properties/<property_pk>/videos/<video_pk>/`.
- Модель `PropertyVideo`; без парсинга URL, авто-платформы и генерации `embed_url`; права `IsCrmUser`.

**Подэтап 8.5 — Backend: публикация объектов в CRM** (выполнено).

- Явные переходы статуса: POST `.../publish/`, POST `.../to_draft/`, POST `.../archive/` (под `/api/crm/properties/`); правила в `properties.crm_publication`.
- Черновик / опубликован / архив: `status`, `is_published`, `published_at`, `archived_at` обновляются только через эти действия; из CRM write (PUT/PATCH) поля `status` и `is_published` убраны.
- Допускаются переходы: draft|moderation → published; published|archived|moderation → draft; draft|published|moderation → archived; из архива в published только через to_draft → publish; повтор того же действия — идемпотентно (без ошибки).

**Подэтап 8.6 — CRM: права доступа к объектам** (выполнено).

- Роли superadmin и admin видят и управляют всеми объектами в CRM; роль realtor — только объектами, где он указан как ``assigned_realtor`` (единственный критерий «своих» в CRM).
- Ограничение и в queryset (списки/вложенные ресурсы), и на уровне объекта: ``IsCrmUser`` + ``IsCrmPropertyStaffOrOwner``; вложенные фото/видео под ``/api/crm/properties/<property_pk>/...`` проверяют доступ к объекту.

**Подэтап 8.7 — Внутренняя логика объектов CRM (доступ, CRUD, PID, риэлтор) (выполнено).**

- **Доступ:** администратор и суперадминистратор видят все объекты в CRM; риэлтор — только объекты с ``assigned_realtor`` = текущий пользователь (см. ``crm_property_queryset_for_user`` / ``user_can_access_crm_property``). Запасного доступа по ``created_by`` при отсутствии ``assigned_realtor`` нет.
- **CRUD в CRM:** создание, просмотр, правка через ``/api/crm/properties/`` (PUT/PATCH); жёсткого DELETE нет, снятие с учёта — архивация (POST ``.../archive/``), как ранее.
- **Идентификатор объекта:** поле ``Property.crm_property_id``, формат **PID** + 6 цифр (``PID000001``, …), уникально, задаётся при первом сохранении новой записи, не пересчитывается при обновлениях; в CRM API поле только для чтения; поиск в списке CRM — по ``crm_property_id``; миграция ``properties.0018_property_crm_property_id`` (backfill существующих строк).
- **Привязка к риэлтору:** связь ``assigned_realtor`` обязательна для каждого нового объекта: проверка в ``Property.clean()`` (админка) и при первом ``save()``; через CRM API администратор обязан передать ``assigned_realtor``; риэлтор при создании всегда назначается ответственным на себя (нельзя передать чужой id); при правке риэлтор не меняет ответственного через API; снять ответственного до ``null`` нельзя. Импорт (14.6): назначение — автор импорта, если он риэлтор, иначе первый риэлтор агентства задачи или первый риэлтор в БД; если ни одного риэлтора в системе нет — строка импорта завершается ошибкой, объект не создаётся.
- **Личный кабинет:** ``/account/properties`` — список и форма создания; ``/account/properties/<id>`` — полная правка объекта (см. подэтап 8.8).

**Подэтап 8.8 — Форма создания и редактирования объекта в CRM (продуктовый этап «форма объекта») (выполнено).**

- **Типы:** в форме кабинета и CRM доступны те же четыре значения ``Property.property_type``, что и в модели: квартира, дом, участок, коммерция; подписи в UI на русском; после создания тип в UI не меняется.
- **Характеристики:** для каждого типа отправляются вложенные блоки ``apartment_details`` / ``house_details`` / ``land_plot_details`` / ``commercial_details`` в ``POST/PATCH /api/crm/properties/`` (сериализаторы ``Crm*DetailsSerializer``); при ``PATCH`` переданные поля характеристик сливаются с уже сохранённой строкой детализации.
- **Описание:** полное описание (и краткое — в той же форме) через поля ``description`` / ``short_description`` CRM write API.
- **Адрес:** город, район, микрорайон, ЖК, улица, дом, публичный текст адреса, флаг скрытия точного адреса — как в модели ``Property``; координаты ``public_*`` и ``real_*`` задаются из формы (в т.ч. после геокода).
- **Автозаголовок:** ``title_generated`` и ``slug`` в CRM write только для чтения; текст заголовка считает backend (``Property.build_generated_title`` / синхронизация при сохранении детализации), отдельного поля «название» в форме нет.
- **Подсказки адреса:** при заданном ``NEXT_PUBLIC_YANDEX_MAPS_API_KEY`` подгружается JS API Яндекс.Карт 2.1 — подсказки ввода и геокод выбранной строки; без ключа остаётся ручной ввод адреса и координат (с пояснением в UI).
- **Точка на карте:** отображение маркера и клик по карте (Leaflet + тайлы OpenStreetMap, как на публичной карточке объекта); блок адреса/карты подключается на клиенте без SSR из-за Leaflet.
- **Загрузка справочников:** форма при монтировании запрашивает два публичных (``AllowAny``) эндпоинта без авторизации: ``GET /api/locations/choices/`` (словари TextChoices: типы ремонта, санузла, отопления и др.) и ``GET /api/locations/cities/`` (список активных городов); оба проксируются через Next.js (``/api/:path*`` → Django); запросы отправляются с заголовком ``Accept: application/json``; при HTTP-ошибке выводится статус в консоли; загрузка районов, микрорайонов и ЖК происходит реактивно при выборе города.
- **Защита от самозацикленного прокси (`ERR_TOO_MANY_REDIRECTS`):** ``next.config.ts`` содержит функцию ``resolveDjangoBaseForApiRewrites()``, которая сравнивает ``BACKEND_URL`` с публичным origin из ``NEXT_PUBLIC_SITE_URL``, ``NEXT_PUBLIC_API_URL`` и ``RAILWAY_PUBLIC_DOMAIN``/``RAILWAY_STATIC_URL``; если они совпадают — значит rewrite уйдёт на сам себя. В этом случае в порядке приоритета используется ``NEXT_PUBLIC_API_URL`` (если хост отличается от ``BACKEND_URL``), затем ``BACKEND_INTERNAL_URL`` (приватный Railway-адрес), иначе — исключение при старте. **Обязательные переменные окружения на Railway (frontend-сервис):** ``BACKEND_URL`` — приватный URL Django-сервиса (``http://<private-hostname>:<port>``), **не публичный** Railway-домен фронтенда; либо альтернативно ``BACKEND_INTERNAL_URL`` — то же самое. ``NEXT_PUBLIC_SITE_URL`` — публичный HTTPS-домен фронтенда (``https://xxx.up.railway.app``). ``NEXT_PUBLIC_API_URL`` — публичный HTTPS-URL Django API (``https://yyy.up.railway.app/api``). Если ``BACKEND_URL`` не задан — используется дефолт ``http://localhost:8001`` (локальная разработка).

### Этап 14 — Инфраструктура, защита, оптимизация, импорт

**Подэтап 14.1 — Сжатие / производные размеры фото объектов** (выполнено).

- **Источник правды:** ``original_file`` хранится как загружен пользователем; производные не перезаписывают оригинал.
- **Стратегия ресайза:** каждый размер строится только из полного растра оригинала (после EXIF-orientation и приведения к RGB для JPEG), длинная сторона ограничивается: large ≤ 1920 px, medium ≤ 1024 px, thumb ≤ 400 px; пропорции сохраняются; изображения меньше лимита **не** увеличиваются.
- **Слишком большой файл:** верхняя граница размера **загрузки** оригинала — **12 МБ**; проверка в ``CrmPropertyPhotoUploadSerializer.validate_original_file`` (русское сообщение для API) и в ``PropertyPhoto.clean()`` (админка и полная валидация модели).
- **Производные:** при сохранении записи, если изменился ``original_file``, заполняются ``image_large``, ``image_medium``, ``image_thumb``; при ошибке обработки оригинал сохраняется, производные очищаются (без «битых» старых файлов от другого оригинала), ошибка пишется в лог.
- **Веб-формат производных:** **JPEG** (качество 85, optimize); оригинал остаётся в исходном формате.
- **Код:** константы и сборка растра — ``backend/properties/property_photo_images.py``; вызов из ``PropertyPhoto.save()`` (пропуск при ``save(update_fields=…)`` без смены ``original_file``, чтобы не ломать reorder и прочие частичные обновления).
